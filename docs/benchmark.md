# Search/browse latency benchmark

Audience: architects and operators assessing the Phase 1 P95 target
(`phases/SPEC.md` "Phase 1 acceptance": "The P95 target for search and
ordinary browsing is under one second against a representative
dataset... If no representative production dataset is available,
create a reproducible synthetic dataset and state its limitations.").
No representative production dataset was available for Phase 1, so
this benchmark uses a reproducible synthetic ADR corpus. See
`docs/architecture.md` for how the pieces measured here fit together
and `docs/operator.md` for how to run the application outside this
benchmark.

## Dataset

Generated by `adriano seed-synthetic`
(`backend/app/services/seed_synthetic.py`,
`backend/app/services/seed_synthetic_gen.py`,
`backend/app/services/seed_synthetic_text.py`) and ingested through
the same `prepare_document`/`ingest_document` path poll and push use
(`backend/app/services/ingest.py`), under
`CatalogStoreProvider.lock_registration`, in batches of 500 -- never
raw SQL.

- **Sizes benchmarked:** 2,000 published records / 100 projects, and
  20,000 published records / 100 projects (the Phase 1 acceptance
  benchmark size). Records are spread round-robin over the projects.
- **Seed:** 42 (the CLI default). Generation is fully deterministic
  for a given `(records, projects, source_id, seed, candidates_ratio,
  decisions_ratio)`: the same inputs always produce byte-identical
  documents (proven by
  `backend/tests/services/test_seed_synthetic.py`).
- **Content shape:** titles built from verb/subject/qualifier word
  lists (e.g. "Adopt Kubernetes for the checkout flow"); bodies are
  "Context" / "Decision" / "Consequences" Markdown sections stretched
  or trimmed to 300-3000 characters.
- **Relationships:** ~15% of records link `updates`/`obsoletes` to an
  earlier record by UUID (catalog-wide, not only within their own
  project, matching how `record_relationships.py` resolves links);
  ~5% are `erratum` records that `corrects` an earlier one.
- **Legacy fields:** ~7% carry a legacy `signed-off-by` list; a share
  of `obsoletes` links are spelled as the legacy `deprecates` alias.
- **Deliberate issues:** ~5% of records carry one deliberate
  validation issue (a missing `uuid`, a malformed `decision-date`, or
  an unknown field), so the seeded catalog exercises the same
  error/warning paths real content does.
- **Candidates:** 10% of published identities (default
  `--candidates-ratio 0.1`) also get a competing candidate row on a
  `feature/...` ref, with a small content variation.
- **Decisions:** 30% of published identities (default
  `--decisions-ratio 0.3`) get an accept/reject decision event
  (80%/20% split), appended directly through the store port
  (`CatalogStore.append_decision`) with a synthetic reviewer identity
  (`adriano-synthetic|synthetic-reviewer`) and the policy id/version
  configured in `bench/catalog.bench.yaml` (`bench` v1).
- **Registration:** `bench/catalog.bench.yaml` declares one
  `filesystem` registration (`id: synthetic`) whose `root` does not
  need to exist -- seeding never calls the source adapter, it writes
  rows directly through the storage port, exactly like push intake
  never calls an adapter. The registration exists only so the API
  serves it (`GET /api/v1/sources`, record provenance) and so the
  approval policy and RBAC (`bench-reader: [read]`) are configured.
- **Limitations of synthetic data:** generated titles/bodies are
  templated, not organic prose, so full-text search relevance (ranking
  quality) is not representative, only its latency; the link/erratum/
  issue ratios are fixed percentages rather than an observed real-world
  distribution; there is exactly one registration and one source type
  (`filesystem`), so this does not measure multi-registration
  contention or the `gitlab` adapter; decision history is flat (no
  multi-round accept/reject/re-accept sequences); body text is
  English-only ASCII, so it does not exercise multi-byte UTF-8 or
  right-to-left text in the full-text search path.

## Environment

- **CPU:** Intel(R) Core(TM) Ultra 5 125U, 14 logical CPUs (`lscpu`).
- **RAM:** 15 GiB total (`free -h`).
- **OS/kernel:** Ubuntu 25.10, Linux 6.17.0-41-generic (`uname -a`).
- **Python:** 3.14.4 (backend `.venv`, matches `requires-python
  ">=3.14"` in `backend/pyproject.toml`).
- **PostgreSQL:** 18.6 (Debian), running in the ephemeral `task db:up`
  container (`adriano-db`, host port 55432, `--tmpfs` data dir --
  i.e. the database files live in RAM, not on disk, which is faster
  than most production disks and is called out as a limitation
  below).
- **Backend:** `uvicorn app.main:app --workers 4` on the host (not
  containerised), matching the `backend/Dockerfile` container default
  (`ADRIANO_WORKERS=4`), port 8100.
- **Client:** `backend/bench/bench.py` (httpx), run on the same host
  as the server (loopback `http://localhost:8100`) -- there is no
  network latency or separate-machine variance in these numbers; a
  real deployment with a client on a different host/network will see
  additional, unmeasured latency.
- **Database:** the ephemeral dev database (`adriano` on port 55432),
  never the test database, per `phases/README.md` "Sub-agent rules".

## Method

1. `task bench:seed` (or standalone for the 2,000 run): resets and
   migrates the ephemeral dev database, then runs
   `adriano seed-synthetic --source-id synthetic --seed 42` for the
   target size.
2. `task bench`: starts the backend (uvicorn, 4 workers, dev auth with
   a throwaway secret generated per run, `ADRIANO_CONFIG_FILE=
   bench/catalog.bench.yaml`), waits for `/healthz`, then runs
   `backend/bench/bench.py`.
3. `bench.py` mints a dev token in-process
   (`app.auth.dev.mint_dev_token`, role `bench-reader`) and resolves
   one project name from `GET /api/v1/facets` and up to 50 sample
   record ids from `GET /api/v1/records` before timing starts.
4. For each scenario, 50 warm-up requests are discarded, then 400
   requests are timed sequentially-issued-but-concurrently-executed
   (`concurrency.ThreadPoolExecutor`) at each of concurrency 1 and 8 --
   at least 300 requests measured per scenario per concurrency, per
   the Phase 1 acceptance benchmark requirement.
5. Scenarios: `free_text` (`q=<random vocabulary term>`), `filtered`
   (`source` + `project` + `state=published`), `needs_approval`
   (`needs_approval=true`), `detail` (`GET /records/{id}` for a random
   sampled id), `sources` (`GET /api/v1/sources`).
6. p50/p95/p99/max/mean latency (milliseconds, wall clock per
   request) and error counts are printed as a table and written to
   a JSON file (`--out`); this report's raw output is saved as
   `docs/bench-2000.json` / `docs/bench-20000.json`.

Reproduce with: `task bench:seed -- --records 2000 --projects 100 &&
task bench -- --requests 400 --warmup 50`, or `task bench` alone for
the 20,000/100 default.

## Verdict against the P95 < 1 s target

- **`free_text`, `filtered`, `detail`, `sources` meet the target** at
  both sizes and both concurrencies: worst observed p95 is 326.9 ms
  (`free_text`, 20,000 records, concurrency 8). `detail` in
  particular -- the scenario this phase was specifically asked to
  check -- is comfortably inside budget after the fix below: p95
  45.8 ms at concurrency 1, 100.8 ms at concurrency 8, down from an
  unfixed ~780 ms per request (see "Detail endpoint optimisation").
- **`needs_approval` misses the target badly** at 20,000 records:
  p95 1848.3 ms at concurrency 1 and 4157.9 ms at concurrency 8 --
  roughly 2x and 4x the 1 s budget. It still meets the target at
  2,000 records (see the table above), so the gap is specific to
  catalog scale, not a general problem with the endpoint. This is a
  **new finding** from this benchmark, not the endpoint phase 05/09
  flagged in advance; see "A second finding" below for the measured
  root cause. Not fixed in this phase (out of the authorized scope),
  reported as SPEC.md criterion 25's "measured gap" for this one
  scenario.

## Detail endpoint optimisation

`GET /api/v1/records/{id}` built its relationship index
(`app.domain.relationships.RelationshipIndex`) from *every* published
row on every request
(`app.storage.port.CatalogStore.list_relationship_summaries`), flagged
in phase 05 as an unoptimised cost to measure here (see
`app/services/record_relationships.py`'s module docstring at the time
and `phases/STATUS.md` phase 05 notes).

**Profiling (before the fix), on the seeded 20,000-record / 100-
project dataset, measuring the storage calls `get_record_detail`
makes, directly, outside HTTP:**

| Step | Time |
|---|---|
| SQL `list_relationship_summaries` (fetch + convert rows) | 628.8 ms |
| Python `RelationshipIndex` build (20,000 summaries) | 141.9 ms |
| `index.view()` | 0.0 ms |
| `get_record` | 3.8 ms |
| `list_identity_siblings` | 2.8 ms |
| `list_decisions` | 3.2 ms |
| **Total (approx. detail cost)** | **780.6 ms** |

`EXPLAIN (ANALYZE, BUFFERS)` of the same `list_relationship_summaries`
query showed Postgres itself executes it in **~82 ms** (parallel
sequential scan + sort over ~20,000 published rows). The gap between
628.8 ms and 82 ms is **not** the database: it is 20,000 iterations of
Python-side row marshalling --
`app.storage.postgres.records._to_summary` (SQLAlchemy row mapping,
`Links.from_dict` parsing every UUID in `links`, enum construction)
run once per row, for a request that, in the end, only ever looks at
*one* record's view of the index.

**Fix implemented** (small, contained, in the files the task
authorized): `app.storage.postgres.records.list_relationship_candidates`
(new function; delegated through `CatalogStore.list_relationship_candidates`
in `app/storage/port.py` and `app/storage/postgres/store.py`) fetches
only the published rows that can possibly affect *one* record's view
-- rows sharing its UUID (duplicate-identity detection), rows whose
UUID is one of its own outbound link targets, and rows that link back
to it via `updates`/`obsoletes`/`corrects` -- pushing the predicate
into SQL instead of filtering 20,000 Python objects down to a handful
after the fact. `app/services/record_relationships.py::_relationship_index`
now calls it instead of the full fetch (record with no valid UUID:
skipped entirely, since nothing can target a UUID it does not have).

*Why this is behaviour-preserving, not just faster:* every row the
full fetch could have used to resolve one record's relationships
matches one of those three conditions; nothing the old code could see
for that record is excluded. `backend/tests/storage/test_records.py::
test_relationship_candidates_match_the_full_index_view` builds a
published catalog with duplicates, a link chain, an erratum and a
dangling target, and asserts the `RelationshipIndex.view()` computed
from the targeted fetch equals the view computed from the full fetch,
for every record. All 404 pre-existing backend tests (which already
exercise `missing_target`, `ambiguous_target`, `duplicate_uuid`,
inbound links and errata through the HTTP detail endpoint) continued
to pass unchanged.

**Profiling (after the fix), same dataset, same measurement (`get_record`
+ `list_identity_siblings` + `build_relationships`, 20 sampled records):**
min 13.6 ms, p50 16.7 ms, max 31.9 ms, mean 18.4 ms -- roughly **40x**
faster than the 780.6 ms the full fetch cost, and comfortably inside
the P95 budget on its own. See the results tables above for the
end-to-end HTTP `detail` scenario, which also includes FastAPI
request handling, Pydantic serialization and the
`list_identity_siblings`/`list_decisions` queries already counted
above.

### A second finding: the `needs_approval` filter (not fixed)

Benchmarking surfaced a **second**, unrelated cost at 20,000 records:
`GET /api/v1/records?needs_approval=true` builds its approval-state
expression (`app/storage/postgres/search.py::approval_state`) as a
`CASE` with two correlated `ORDER BY ... LIMIT 1` subqueries plus a
correlated `EXISTS`, evaluated once per row, for both the `count(*)`
and the paginated `SELECT` (so twice per request). `EXPLAIN (ANALYZE,
BUFFERS)` of just the `count(*)` half, on the same 20,000-record / ~6k-
decision-event dataset, measured **~750-880 ms**: the per-row
correlated-subquery index lookups are individually cheap (each a
sub-millisecond `Index Scan` on `uq_decision_event_identity_digest`),
but Postgres ran that lookup **21,967** and **17,305** times
respectively for the two subqueries (once per catalog row), and query
JIT compilation added a further ~200-400 ms on top. This is a
different module (`app/storage/postgres/search.py`, not
`app/services/record_relationships.py`) and a schema/query-shape
problem (most likely needing a precomputed or materialized approval
state, or a `LEFT JOIN LATERAL` restructuring, to avoid the per-row
round trips) -- too large a change to qualify as the "small, safe,
contained" fix this task authorized, so **it was not implemented**.
Reported here as a gap for the coordinator/product owner: the
`needs_approval` scenario in the results tables above is the measured
evidence; a follow-up phase should profile and fix
`app/storage/postgres/search.py` the same way this phase fixed
`record_relationships.py`.

## Limitations and how to reproduce

- This is a synthetic dataset on a single developer machine with a
  `--tmpfs` (RAM-backed) database and a same-host client; a real
  deployment's absolute numbers will differ, mainly from disk I/O,
  network latency between client and server, and real-world query
  plans over organically grown data (indexes, table bloat, vacuum
  state) rather than a freshly migrated, freshly vacuumed database.
- Candidate/decision ratios, link ratios and the vocabulary are fixed
  generator parameters, not measured from a real catalog; treat the
  *shape* of the results (which scenario is slow, and why) as the
  evidence, not the exact millisecond values, when extrapolating to a
  different deployment.
- Reproduce end to end with `task bench` (20,000/100; pass
  `--records`/`--projects` to `task bench:seed` first for a different
  size) from a clean checkout, after `cp .env.example .env` is not
  even required -- `task bench` sets every environment variable it
  needs itself. See `backend/bench/bench.py --help` for every
  benchmark parameter (request count, warm-up, concurrency list,
  base URL, token).
